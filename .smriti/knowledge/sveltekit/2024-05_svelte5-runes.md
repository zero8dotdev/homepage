# Decision: Svelte 5 runes throughout — no legacy store pattern

## What was decided
zero8-sveltekit runs on Svelte 5 with runes (`$state`, `$props`, `$derived`, `$effect`) — not Svelte 4 `export let` and writable stores.

## The rune mapping

| Svelte 4 | Svelte 5 | Notes |
|---|---|---|
| `export let foo` | `let { foo } = $props()` | Props are destructured |
| `let x = 0` (reactive) | `let x = $state(0)` | Explicit reactive declaration |
| `$: y = x * 2` | `let y = $derived(x * 2)` | Derived values |
| `$: { ... }` | `$effect(() => { ... })` | Side effects |
| writable store | `$state` | Local state only |

## The warning to know: `state_referenced_locally`

```
This reference only captures the initial value of `data`.
Did you mean to reference it inside a closure instead?
```

This fires when you do:
```svelte
<script>
  let { data } = $props();
  const posts = data.posts; // ← captures snapshot, not reactive
</script>
```

Fix: reference `data.posts` directly in the template, or use `$derived`:
```svelte
const posts = $derived(data.posts.map(...));
```

These warnings appear in the build output but don't break anything — they're Svelte 5 linting the component reactivity model. In this codebase they exist in `+page.svelte`, `blog/+page.svelte`, and `blog/[slug]/+page.svelte` and are tracked as known warnings.

## When to suppress vs fix
If the `data` prop truly won't change after component mount (server-rendered page data rarely does), the warning is a false positive. Document it. Don't invest in converting every instance to `$derived` unless the component actually needs reactivity on re-navigation.

## Component props typing
```svelte
<script lang="ts">
  let { data }: { data: PageData } = $props();
</script>
```
`PageData` is generated by `svelte-kit sync` from the `+page.server.ts` return type. Run `pnpm prepare` (or let the dev server do it) if types are stale.
